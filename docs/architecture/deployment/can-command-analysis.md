## 1. 区分输入、下发和反馈

| 层级 | 内容 | 能说明什么 |
|---|---|---|
| 手动输入 | `control/manual_request` 六轴字段，顺序 Fx、Fy、Fz、Mx、My、Mz | 各轴 -100～100 的操作档位，单位不是 N 或 N·m |
| 物理力输入 | `control/wrench_request` | 模型请求，力为 N，力矩为 N·m；不使用手动起步增益 |
| 分配结果 | `control/allocation` | 分配力、建议 RPM、死区后的模型合力及状态 |
| 下发请求 | `actuators/thrusters/setpoint` 与 CAN ID `0x100` | 请求电机按哪些转速、运行位工作 |
| 电机反馈 | `actuators/thrusters/state` | 需结合有效性、时间和节点判断实际电机状态 |

本文话题均默认位于 `/underwater_robot/` 命名空间。
手动入口默认 `manual_axis_signs=[-1,1,1,-1,1,-1]`，顺序为 Fx、Fy、Fz、Mx、My、Mz。
分配和反算力矩采用八推进器中心 thruster_center；物理力入口保持 NED 轴向。
CSV 中若只有 `0x100`，就没有足够证据证明电机实际达到目标转速或产生指定推力。
抓包工具标记的 `Rx` 表示工具接收到了总线帧，不表示它是电机反馈。

## 2. 手动档位如何变成转速

键盘程序按下列方式修改对应轴，未操作的其他轴保持原值：

| 按键 | 增加 / 减少的轴 |
|---|---|
| W / S | Fx |
| T / F | Fy |
| I / J | Fz |
| Y / G | Mx，横滚，终端中也记作 K |
| U / H | My，俯仰，终端中也记作 M |
| A / D | Mz，偏航，终端中也记作 N |

按键累加操作量，松开键不会自动归零，换一个轴操作也不会清除原轴。
例如先将 Fy 加到 3，再把 Mx 减到 -1，输入是两轴组合。
`Q` 退出并请求停机；完整退出和超时行为见 [README 键盘控制](../../../README.md#键盘控制)。

设六轴绝对值的最大值为 `L`。当前分配器先按归一化六轴方向进行 QP 分配，
归一化方向按 manual_axis_signs 逐轴映射，再使用统一增益。当前布局的单轴起步峰值为 1200 RPM；
组合方向的峰值可能升高，以确保所有必要通道越过死区。单轴最大通道的目标转速为：

```text
L < 1：所有目标转速为 0
1 <= L <= 100：peak_rpm = 1200 + 4800 × (L - 1) / 99
```

| L | 1 | 2 | 3 | 5 | 7 | 8 | 10 | 13 | 100 |
|---|---|---|---|---|---|---|---|---|---|
| 最大通道 RPM，取整后 | 1200 | 1248 | 1297 | 1394 | 1491 | 1539 | 1636 | 1782 | 6000 |

统一缩放后，各通道仍执行 `abs(raw_rpm) < 1000 → 0`，其余舍入并限幅到 ±6000。
零档到 1 档的下发值会直接跨到约 1200 RPM，不能把抓包里的阶跃解释成电机实际瞬时加速。

可用 `L ≈ 1 + (最大绝对转速 - 1200) × 99 / 4800` 估计最大档位，
但前提是采用当前默认参数和手动入口。该公式不能恢复全部六轴输入，
也不适用于物理力入口或不同参数的系统。

实现来源：[分配器](../../../internal/underwater_control/src/allocation/allocator.cpp)、
[转速映射](../../../internal/underwater_control/src/allocation/linear_rpm.cpp)、
[键盘输入](../../../src/sensors_cpp/src/manual.cpp)。

## 3. 解码 CAN 指令

当前电机下行是 CAN ID `0x100`、24 字节 CAN-FD 数据。
以下偏移从 CAN payload 的第一个字节开始计数，不包括 USB 串口的 AA55 封装。

| 字节偏移，从 0 开始 | 长度 | 含义 |
|---|---|---|
| 0 | 1 | 版本，当前为 `01` |
| 1 | 1 | 命令：`10` 为 SPEED_VECTOR，`11` 为 RUN_VECTOR |
| 2 | 1 | NodeMask，当前为 `FF`，选择节点 1～8 |
| 3 | 1 | RunMask，bit 0～7 分别对应节点 1～8 |
| 4～5 | 2 | 16 位小端序号，每帧递增，允许 65535 后回绕到 0 |
| 6～7 | 2 | 保留，当前为 `00 00` |
| 8～23 | 16 | 节点 1～8 的转速槽，每槽为小端有符号 int16，单位 rpm |

**转速值取自 `0x10`；`0x11` 的转速槽在本项目中全部填零，不代表目标转速又被清零。**
同样，`0x10` 中 RunMask 为零，不表示当前运行中的电机被停掉。
应把两类命令按时间顺序联合解释。

以 111.csv 的第 405、406 条记录为例：

```text
01 10 FF 00 94 01 00 00 50 FB 50 FB A4 04 A4 04 00 00 00 00 00 00 00 00
01 11 FF 0F 95 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

- `50 FB`：小端数值为 `0xFB50`，按 int16 解码为 `-1200`。
- `A4 04`：解码为 `+1188`。
- 转速向量为 `[-1200,-1200,1188,1188,0,0,0,0]`。
- `RunMask=0F`：请求节点 1～4 运行，5～8 停止。
- `94 01` 和 `95 01`：序号分别为 404、405；CSV 记录序号从 1 开始，二者不要混淆。

常见运行掩码：

| RunMask | 请求运行的节点 |
|---|---|
| `00` | 全部停止 |
| `0F` | 1～4 |
| `F0` | 5～8 |
| `FF` | 1～8 |

运行时：先发 SPEED_VECTOR 更新速度，再发 RUN_VECTOR 更新运行位。
全停时：先发 RUN_VECTOR、RunMask=0，再发全零 SPEED_VECTOR。
只看到零速度帧，不能代替检查明确的停止帧。
抓包可能从一组命令的中间开始，分析时应按命令和序号配对，不能固定把每两行视为一组。

编码依据：[motor_commands.cpp](../../../internal/underwater_mcu_gateway/src/commands/motor_commands.cpp)。

## 4. 从转速判断运动方向

当前 fan1～fan8 对应 CAN 节点 1～8，`motor_direction=[1,-1,-1,1,1,1,-1,-1]`。
模型采用北东地（+X 北、+Y 东、+Z 地）。
下表的 +Fx/+Fy/+Fz/+Mx/+My/+Mz 指 NED 模型正方向；手动输入需按上述逐轴符号映射，
不能将六个手动轴全部视为与 NED 同号或全部反号。
1～4 号为水平推进器，5～8 号为垂直推进器。以下为主要输出的典型符号模式，
`+/-` 表示正负目标转速，不能仅凭符号证明原始输入为单轴；小补偿通道可能已被死区去掉。

| 主要输出方向 | 1～4 号典型符号 | 5～8 号典型符号 |
|---|---|---|
| +Fx | `- + - +` | 可存在俯仰补偿，低档可能全零 |
| +Fy | `- - + +` | 可存在横滚补偿，低档可能全零 |
| +Mz，偏航 | `- - - -` | 通常为零 |
| -Mz，偏航 | `+ + + +` | 通常为零 |
| -Mx，横滚 | 通常为零 | `+ - - +` |
| +My，俯仰 | 通常为零 | `- - - -` |
| +Fz，向下 | 通常为零 | `+ + - -`；低档可能为 `+ + 0 0` |

反方向通常对应符号反转。组合输入应使用完整的几何合成，不能套用单行符号表。
在未确认机体轴定义、观察视角和安装方向前，不把正负轴直接改写成“顺时针”“抬头”等描述。

## 5. 分析一份新 CSV

1. **记录来源。** 保存文件名、采集日期、SHA-256、导出工具和过滤条件；原始 CSV 保存在仓库外。
2. **确认文件结构。** 检查编码、列名、记录数、CAN ID、DLC 和数据字节数；中文导出可能是 GB18030。
   此类 CSV 的时间可能写成 `="20:33:07.809"`，应当作文本时间读取。
3. **解码所有相关帧。** 先按 ID/命令分类，保留记录号、时间标识、序号、RunMask 和八路 RPM。
   不把 int16 负转速读成无符号大整数。
4. **验证顺序与掩码。** 检查序号连续性、回绕、保留位、速度范围、速度/运行帧配对，以及最后明确停止帧。
   对本项目，运行帧的位应与此前配对速度向量的非零通道对应。
5. **合并相同输出。** 将连续相同 RPM 向量合并成阶段，记录首条、末条和下一次变更。
   某状态的持续时间应计算到下一次变更，不只是最后一条相同数据的时间。
6. **绘制时间曲线。** 水平与垂直推进器分别绘制，另画运行掩码；保留正负号，用阶梯曲线表示保持的指令。
7. **解释力和方向。** 对照布局合成模型力矩，区分确定的输出、推定的输入，以及无法确认的实机响应。

时间分析优先使用已经确认单位的单调时间标识。111/112 实例中按微秒换算的时间标识跨度
与系统时间约 25.6/40.3 秒相符，适合估算约 20 ms 的更新周期。
系统时间列有批量刷新现象，多个帧可能显示同一毫秒，不能据此判断同时发送或突发抖动。
新工具的时间标识单位必须重新确认。本文实例时间线使用导出的系统时间，周期使用时间标识差值。

序号连续只说明在所观察指令流中未发现缺号，不能证明总线完全无误码，
也不能证明每台电机都执行成功。若只导出了筛选后的 `0x100`，不能据此断言总线上没有反馈帧。

## 6. 反算模型力与死区影响

当前临时比例为 `6000 rpm ↔ 500 N`。默认节点映射和方向下：

```text
T_i = rpm_i × motor_direction_i / 12     # 临时模型推力，N；当前节点顺序等于推进器顺序
F = Σ(axis_i × T_i)                      # axis_i 为单位方向向量
M = Σ((position_i - center) × (axis_i × T_i)) # center 为八点几何中心；外层 × 为叉乘
```

这里 `axis_i × T_i` 是向量乘标量。位置与方向取自
[allocation.yaml](../../../internal/underwater_control/config/allocation.yaml)，方向须归一化。
若修改了节点映射或 `motor_direction`，需先还原至推进器顺序和推力正方向，再合成。
该比例未做真实推进器标定；反算值是“按下发 RPM 预测的模型输出”，不是实测力，也不是原始输入。

当前八推进器中心的 z=-0.040532 m，四台水平推进器相对中心的高度为零，
纯 Fx/Fy 不再需要补偿底部原点导致的俯仰/横滚力矩。以下是旧 base_link 原点的历史公式：

```text
纯水平 Fx 输出附带 My = -0.040532 × Fx
纯水平 Fy 输出附带 Mx = +0.040532 × Fy
```

历史例子：112.csv 的侧移峰值向量 `[-1297,1297,-1221,1221,0,0,0,0]`，
按 2026-10-08 采集时旧配置（motor_direction 全为 +1）合成约为 `Fy=296.75 N、Mx=12.03 N·m`。
该历史向量不能按当前 motor_direction 合成为同一侧移输出。
即使上层意图是纯侧移，低于 1000 RPM 的姿态补偿被清零后，下发结果也可能带横滚力矩。

组合输入还会触发另一种变化：所有通道共同缩放时，强通道保持起步转速，弱通道可能跨入死区。
所以增加某个力矩轴后，原平移通道可能突然归零。仅凭 CAN 无法区分这与用户清零平移输入，
必须同时查看原始输入、死区前分配和死区后结果。

## 7. 同步记录 ROS 输入和反馈

在已经运行的系统上，以下命令只订阅或记录话题，不发布运动指令，也不启动新的网关。
每个终端先进入工作空间并加载环境：

```bash
cd /home/lamost/UnderWater-Robot-ROS2
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 topic echo /underwater_robot/control/allocation
```

重点比较：

| 字段/话题 | 用途 |
|---|---|
| `control/manual_request` | 原始六轴手动档位，确认换轴时是否保留了原轴 |
| `control/wrench_request` | 物理力接口的原始请求 |
| `allocation.requested_wrench` | 手动模式下是放大后的等效模型请求，不是原始档位 |
| `thruster_force_n`、`allocated_wrench` | RPM 死区前的模型分配 |
| `proposed_motor_rpm`、`modeled_rpm_wrench` | 死区后的建议目标及模型合成 |
| `rpm_deadband_applied`、`rpm_saturated` | 是否应用了死区或转速上限 |
| `armed`、`input_fresh`、`gateway_ready`、`solver_ok` | 是否具有有效、可发送的控制状态 |
| `actuators/thrusters/setpoint` | 门禁之后交给网关的目标；预览建议值不一定会下发 |
| `actuators/thrusters/state` | 实际反馈，需检查新鲜度与有效性 |

使用独立目录记录一组完整证据，`Ctrl+C` 结束录包：

```bash
mkdir -p ~/robot_data
ros2 bag record -o ~/robot_data/can-command-$(date +%Y%m%d-%H%M%S) \
  /underwater_robot/control/manual_request \
  /underwater_robot/control/wrench_request \
  /underwater_robot/control/allocation \
  /underwater_robot/actuators/thrusters/setpoint \
  /underwater_robot/actuators/thrusters/state \
  /underwater_robot/gateway/status
```

当前默认 [录包清单](../../../internal/underwater_bringup/config/recording/topics.yaml)未包含上述全部控制话题，
针对指令分析时应使用这里的显式列表。记录当前配置、现场使用的源码版本，以及 CAN 工具与 ROS
时钟的对齐方式，避免把不同时间基准的消息直接相减。

## 8. 常见现象与判断边界

| 观察到的现象 | 先检查什么 |
|---|---|
| `0x11` 的转速字节总为零 | 这是当前运行帧的编码方式；目标速度看配对 `0x10` |
| 正反转数值似乎变成六万多 | 是否按小端有符号 int16 解码 |
| 低档下垂直推进器不动 | 其分配转速是否小于 1000 RPM，被死区清零 |
| 加横滚后侧移输出消失 | 原始 Fy 是否保留；统一缩放后水平通道是否落入死区 |
| 1、2 与 3、4 号转速略有不同 | 布局及分配比例；指令差异不能当作电机速度跟踪误差 |
| 一段目标长时间不变 | 键盘档位会保持；继续看输入时间戳和更新周期 |
| CSV 有指令但不知道是否真的转了 | 补录电机反馈；CAN 下发和真实运动是不同证据 |
| 最后看到转速为零 | 继续确认 RUN_VECTOR 的运行位已清零 |

完整实例与两张曲线见 [111/112 抓包记录](../../experiments/2026-10-08-can-command-analysis.md)。
